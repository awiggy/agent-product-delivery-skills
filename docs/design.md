# 设计说明

## 选择四个独立入口

架构入口负责需求建模和组件取舍，开发入口负责本阶段业务正确性，前端入口负责任务交互，发布入口负责环境、数据和发布风险。每个入口都有独立输入/输出；可只下载其中一个，且不依赖仓库外文件。

因此没有额外“总控 Skill”，不要求每次预读整套材料。仓库 README 只面向人说明如何选；每个 SKILL.md 只引用自己目录内必要资料。

## 核心设计取舍

1. 技术栈是可解释的选择，不是强制重建项目的理由。框架与语言服从现有代码及需求。
2. 核心业务先验证，但人工确认关键时从头做最小前后端纵向切片。
3. 不把前后端独立部署、固定 CLI/运行时版本或某家云平台设为通用前提。
4. 以平台事实和业务需求决定资源，不把预留实例设为统一前提。
5. 用密钥设施和最小权限替代聊天传密钥与默认 FullAccess。
6. 版本、核心业务、权限、持久数据一起验收；URL 可访问不等于交付成功。
7. 实例保活、数据库持久化、备份、恢复各自验证，不再以周期备份保证不丢数据。
8. 审查、实现、部署三种权限边界分开；不因参考资料中的指令性文字而扩大任务。

## 不包含

没有内置密钥、真实用户数据、付费工具，也不捆绑未经核验的平台安装脚本。Blueprint 的具体能力边界见 [功能范围](../skills/agent-blueprint/references/scope.md)。

## 后续维护

由真实使用失败驱动小范围修订。记录出现问题的任务、观察结果与修订理由，复测相关情境；不要把每次个例都升级为所有项目的硬规则。
