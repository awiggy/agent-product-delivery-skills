# Agent 架构蓝图

从业务需要推导架构，不从组件清单反推需求。这里的 Harness 指围绕模型的工具、知识、观察、行动接口和权限控制，不是必须采用的某个框架。

## 范围与读取

- 只有点子、需求不完整：读 [需求澄清](references/discovery.md)，区分已知事实、假设和待确认项。
- 已有 PRD 或代码：先读相关需求、现有架构与接口，再读 [组件决策](references/component-decisions.md)，只处理本次涉及的能力。
- 涉及工具、权限、记忆、并行或复用示例：读 [运行边界](references/runtime-boundaries.md)。
- 需要方案文档时参考 [蓝图模板](assets/blueprint.md)，按任务删减，不强制所有小任务产出大文档。

## 推导步骤

1. 确定用户需要的是澄清、方案、评审还是已授权实现。蓝图任务到方案交付为止；不把“最终可上线”当作本次部署授权。
2. 提取目标用户、一次输入到结果的闭环、数据/系统来源、禁区和成功标准。矛盾需求先明确，例如禁止数据出域却指定外部模型。
3. 比较普通程序、固定工作流、动态 Agent 与混合方案。确定性步骤优先交给代码；只有运行时确需推理选工具时才增加 Agent 自主性。
4. 将需求映射到五项：需要哪些工具、知识从何而来、如何观察结果、行动用什么接口、谁有权批准。每个外部动作都需有观测证据和权限边界。
5. 选择最少必要组件。对每项写需求依据、缺少它的后果、维护成本和更简单的替代方案；不因“完整”而默认上团队、MCP、记忆或调度。
6. 给出模块/数据流、工具契约、模型与上下文策略、失败降级、成本/时间/步数上限和验收方法。大型方案可用七层视角检查遗漏，小型方案可合并或标不适用。
7. 列出需确认的关键选择与下一阶段输入。若用户已经批准方案并要求实现，不重复索要同一批准；只处理新增的实质分歧。已有项目按增量设计，不为了蓝图推翻技术栈。

方案是设计，不是已运行产品；测试计划不是测试结果。对未运行、未测量、未确认的内容明确标注。不要仅凭生成骨架或满足几条文档清单就称“生产级”。
